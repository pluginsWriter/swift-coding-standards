## 为「Windows 编码规范」做可行性分析（15:03，用户提问，仅分析未动手建）

用户问：要实现 Windows 编码规范，① 有哪些常用/官方文档 ② Windows 侧标准有哪些、swift-format/SwiftLint

（放在 `.workbuddy/` 下，不进 git、不污染已发布 skill）。核心结论：

1. **不存在「Windows 官方编码规范」** —— Windows 是平台不是语言，规则分散在四层（语言与运行时 /
   领域合规 / 平台与界面 / 跨语言底座）。这是与 Swift 最本质的差异。
2. **病根相反**：Swift 是「官方无单一格式标准、生态只有两个工具」→ 我们做的是补缺口；Windows 是
   「标准与工具太多、规则上千条」→ 新 skill 的目标应改为**收敛选择 + 分级 + 可验证的基线迁移**。
3. **对应物**：`dotnet format` ≈ `swift format`，`.editorconfig` ≈ `.swift-format`，Roslyn analyzers
   （CAxxxx/IDExxxx）≈ SwiftLint；且 .NET 侧多一项 Swift 没有的能力 —— `EnforceCodeStyleInBuild`
   + `TreatWarningsAsErrors` 让「跑不过就提交不了」压在编译上。C++ 侧靠 clang-format/clang-tidy
   + MSVC `/W4 /WX /analyze`；PowerShell 只有 PSScriptAnalyzer（**无格式器**）；驱动侧是认证级：
   WHCP 强制 CodeQL + DVL，且驱动版 Code Analysis 已宣布退役。
4. **方案**：A 单栈单 skill（推荐起点）→ B 伞形多栈（description 变胖、自检变矩阵）→ C 元框架模板
   （需先有第二份实例，放第二步）；**D 扩展当前 skill 明确不推荐**（违反薄入口 + 已发布仓库改名断链）。
5. **新发现的硬约束（Swift 侧没有的）**：快照的**版权边界**。《Framework Design Guidelines》是书不可
   快照；Microsoft Learn 许可须逐页核实 → 若合法快照源不足，`verify_citations.sh` 的「逐字校验」要
   降级为「引用条目存在性 + 链接可达性校验」。这一条必须在设计阶段定，不能事后补。
6. 待用户确认目标栈后再动手建 skill。

### 三个真 bug（都是首版漏掉、由核验抓出的）

1. **`run_awk`/`run_sed` 用 `mv` 替换文件会丢可执行位**（755 → 644）→ 变换前记 `stat -f %Lp`、`mv` 后
   `chmod` 还原。由「可执行位断言」抓出。
2. **awk `getline` 次数写多了**：`remediate.sh` 的评审编号注释只占 **2 行**，我按 3 行处理，
   吃掉紧随其后的 `if [ -n "$DIRS" ]; then` → 脚本语法错误。
   **这一条断言全绿也没抓到**（内容类断言查不出结构被改坏），是独立跑 `bash -n` 才发现的。
   → 已把「`bash -n` 逐个检查发布树脚本」补进断言集。
3. **禁词正则把全角字符写进 `[...]` 字符类**（`[（(][CD][0-9]+[（(]`），实测**同一条正则
   在 `grep -r` 与 stdin 下结论不一致** → 改为字符类只用 ASCII、边界另加非标识符字符，
   并先对全量跑一遍确认无假阳性（`SC2206` 这类 shellcheck 编号极易被误判成评审编号）。

**另一条 sed 陷阱**：模式里未转义的 `*`——`**` 在 BRE 里是「零个或多个 `*`」而非两个字面星号，
导致三条变换静默不匹配（只有断言报 FAIL 才发现）。**避开 `*`，改锚定不含星号的子串。**

**方法论（值得记住）**：内容断言（禁词/行数/锚点/权限）**全绿 ≠ 产物可用** —— 产物含可执行文件时，
必须独立跑一次可执行性检查。断言的价值也不在于「通过」，而在于它每次都能指出我还漏了什么。
